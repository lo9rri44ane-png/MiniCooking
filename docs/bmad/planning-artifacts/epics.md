# 新游戏 - Epic 与可验收任务

## Overview
按用户授权拆分已确认设计，不代表所有任务已开发、已试玩或获全量设计批准。规则以 GDD 最新确认段落覆盖旧段落。独立 architecture.md、UX 规格尚未形成；已有框架和实现范围只作为技术约束，不宣称架构审核通过。

任务按顺序可独立验收；每个 Story 控制在单次开发会话可完成的范围。Epic 1 先提供可在逻辑回放中验收的玩法，Epic 2 接入 Creator；Epic 3、4 各自提供开发者价值，不要求前面任务依赖后面的工具。

## Requirements Inventory
### Functional Requirements
- FR1：配置关卡棋盘、障碍、单厨师起点、材料、设备操作格、配方、客人队列、背包容量与步数预算。
- FR2：四方向滑到障碍停止；有效位移一步，零位移不扣步。
- FR3：沿途逐格拾取所有种类材料；每份占一格；达到容量立即失败，停止后续行动。
- FR4：仅在设备操作格停下才制作；设备支持多配方；制作不额外耗步。
- FR5：按可见订单顺序，真实消耗材料并批量制作交付；不支持或缺料的订单跳过。
- FR6：最多三客同时在场，全部需求完成后离开，按预设顺序补位；候场订单可查看但不能预做。
- FR7：同次停靠对补位客人继续制作，直至无可制作订单或全部完成。
- FR8：单厨师连续完成全关订单，最后表现为下班；保留全关步数限制及满包失败。
- FR9：编辑关卡、保存草稿、导入导出、试玩并保留编辑内容。
- FR10：按全关全部订单核对每类材料数量恰好匹配，检查非法配置。
- FR11：最少有效滑行求解，区分最优、仅可行、无解和计算未确定，提供解法回放。
- FR12：算法辅助调整步数与布局，支持约束、预览、应用和撤回。

### NonFunctional Requirements
- NFR1：固定 Creator 3.8.8，沿用当前 2D 框架，不重建项目、不默认打包、不自动另开引擎。
- NFR2：游戏、编辑试玩、求解、回放共享确定性规则；动画与逻辑分离。
- NFR3：元数据由编辑器生成；监听与资源成对清理；页面销毁后不继续异步写入。
- NFR4：求解可取消、有时间和状态限额；超时不冒充无解或最优，过期结果不回写。
- NFR5：Creator 实际预览才算展现功能验收；类型检查不替代运行。
- NFR6：失败导入与存档损坏不覆盖原数据；不使用付费生图或外部消息。

### Additional Requirements
复用 Application、UIService、SaveStore、CocosAssets 和 AudioService；玩法放 features/kitchen，纯逻辑不导入 cc。无需新建引擎工程或基础模板。具体新文件只在对应任务需要时创建。

### UX Design Requirements
无独立已批准 UX 文档。已确认：订单显示材料需求、背包与步数可见、候场可查看、制作动画、最终下班表现。小动物厨师＋卡通人类＋迷你厨房只作为美术方向，不把正式素材制作纳入已批准任务。

## 状态与未决项
下列“可开始”表示任务规格已可编写，不代表用户已授权本轮开始编码。设备操作格采用关卡显式坐标，不擅自固定上／下方；物件重叠合法性、同一操作格多设备等冲突需在 1.1 列出校验提案。
必须在相关任务开始前确认的细节：多个客位同时空出时补位顺序、补位后新旧订单显示优先级、最后一步胜败检查顺序。分别由 1.6、1.8 先提供具体决策表；未批准不宣称这些任务可直接实现。
成长解锁、币值、星级、装修、正式美术、玩家撤销／提示／加步、微信抖音发布不混入当前承诺，另列待设计清单。6关是实现范围中的建议，不视为用户已确认的数量。


## Epic 1: 核心规则可回放

### Story 1.1: 加载并校验一份关卡

状态：可开始；依赖：无；覆盖：FR1、FR10。

作为关卡作者，我希望读入合法关卡并得到明确错误，以便避免配置错误进入试玩。

**Acceptance Criteria**

- **Given / When / Then**：给定合法小关卡，加载后保留所有订单、配方、操作格和队列参数；给定未知材料或配方引用，返回字段路径与原因。
- **Given / When / Then**：给定订单配方展开后的材料清单，校验每类材料精确匹配全队列需求；缺一份或多一份均报错。
- **Given / When / Then**：容量为C且单份配方材料数大于等于C时，报告按即时满包规则不可制作；校验失败不修改输入数据。


### Story 1.2: 执行四方向滑行与计步

状态：可开始；依赖：1.1；覆盖：FR2。

作为关卡作者，我希望回放厨师滑行终点，以便验证路线。

**Acceptance Criteria**

- **Given / When / Then**：给定墙和边界，四方向指令停在阻挡前最后可走格，不能穿墙。
- **Given / When / Then**：有位移只消耗一步，紧邻墙导致零位移不扣步；相同输入结果一致。
- **Given / When / Then**：输出经过格子的有序记录供后续拾取使用，不依赖Cocos或动画帧率。


### Story 1.3: 逐格拾取并立即判满包

状态：可开始；依赖：1.2；覆盖：FR3。

作为玩家，我希望明确看到背包压力，以便规划收集路线。

**Acceptance Criteria**

- **Given / When / Then**：给定连续多个材料格，按经过顺序每份拾取一次，原棋盘材料相应移除，种类不限。
- **Given / When / Then**：容量7且已有6份时，下一份立即失败，之后的格子、设备和交付不再处理。
- **Given / When / Then**：容量可配置；重复方向回访已拾取格不重复添加；材料齐全不会在路上自动合成。


### Story 1.4: 停靠支持多菜谱的设备

状态：可开始；依赖：1.3；覆盖：FR4。

作为玩家，我希望在合适设备前制作，以便将材料转为订单。

**Acceptance Criteria**

- **Given / When / Then**：给定设备支持多个配方，仅停在指定操作格且材料满足时产出制作事件。
- **Given / When / Then**：途中经过操作格不制作，材料不足或设备不支持时不消耗材料。
- **Given / When / Then**：制作按份扣材料且直接交付，不生成需运输的成品，也不额外扣步。


### Story 1.5: 按订单优先级批量制作

状态：可开始；依赖：1.4；覆盖：FR5。

作为玩家，我希望一次做完可制作食物，以便释放背包空间。

**Acceptance Criteria**

- **Given / When / Then**：给定A、B共享一份面包，A展示在前，制作A后用剩余材料检查B，不复用同一材料。
- **Given / When / Then**：前序订单缺料或设备不支持时跳过，后序满足的订单仍制作。
- **Given / When / Then**：一客同菜多份按需求与材料逐份制作，已完成需求不重复执行；订单顺序和结果可回放。


### Story 1.6: 查看三客位和固定候场队列

状态：待补位细则确认；依赖：1.5；覆盖：FR6。

作为玩家，我希望知道当前和后续需求，以便提前规划。

**Acceptance Criteria**

- **Given / When / Then**：提供空位分配与显示顺序决策表供确认；未确认不暗设随机顺序。
- **Given / When / Then**：初始最多三客在场；一客部分需求完成不离开，全部完成才补位。
- **Given / When / Then**：候场订单可读取但不可提前制作；相同关卡重复运行出场与优先级相同。


### Story 1.7: 同次停靠连续处理补位订单

状态：前置规则完成后可开始；依赖：1.6；覆盖：FR7。

作为玩家，我希望自动完成新客人的可做订单，以便避免无意义来回移动。

**Acceptance Criteria**

- **Given / When / Then**：给定当前设备支持补位客人菜谱且材料足够，在同次停靠继续制作，不需新移动。
- **Given / When / Then**：持续到当前设备无法再做任何在场需求或全关完成，不重复消费或漏掉可制作订单。
- **Given / When / Then**：有限订单处理必终止；事件记录包含制作、客人离开和补位顺序，供动画与求解使用。


### Story 1.8: 结束关卡并可靠重置

状态：待最后一步判定确认；依赖：1.7；覆盖：FR8。

作为玩家，我希望得到正确胜败结果，以便明确是否完成。

**Acceptance Criteria**

- **Given / When / Then**：给出最后一步完成订单应胜利、否则步数耗尽失败的判定提案，确认后固化测试。
- **Given / When / Then**：全部客人含候场均完成才胜利；满包立即失败后不得继续制作或反转结果。
- **Given / When / Then**：结束后忽略输入，重试从原始关卡重建位置、材料、背包、队列和步数，不污染原配置。


## Epic 2: 在 Creator 试玩

### Story 2.1: 在现有页面中操作棋盘

状态：前置完成后可开始；依赖：1.8；覆盖：FR2、NFR1。

作为玩家，我希望在Creator直接滑动试玩，以便体验路线解谜。

**Acceptance Criteria**

- **Given / When / Then**：从现有首页进入厨房页，用清楚的占位图显示起点、墙、材料、设备与操作格，不重建启动场景。
- **Given / When / Then**：触摸滑动发出单方向动作，桌面方向键支持同规则；动画中不重入，零位移不扣步。
- **Given / When / Then**：重复进入退出页面后不重复监听；当前Creator预览可操作并留截图和控制台记录。


### Story 2.2: 显示背包、步数与客人队列

状态：可开始；依赖：2.1；覆盖：FR3、FR6。

作为玩家，我希望读懂当前限制和订单，以便规划下一步。

**Acceptance Criteria**

- **Given / When / Then**：显示容量对应的槽位、材料种类与数量、剩余步数，拾取后与逻辑状态一致。
- **Given / When / Then**：顶部最多三个客人，展示每份食物材料需求与完成进度；可查看候场订单及次序。
- **Given / When / Then**：不同材料除颜色外也有名称或形状区分；常见竖屏预览下关键操作不被安全区遮挡。


### Story 2.3: 播放批量制作及补位动画

状态：可开始；依赖：2.2；覆盖：FR4、FR5、FR7。

作为玩家，我希望看清做了哪些菜，以便理解背包释放和订单完成。

**Acceptance Criteria**

- **Given / When / Then**：按规则事件序列播放制作、材料消耗、交付与客人补位，不由动画另算配方。
- **Given / When / Then**：补位连做完整展示，不重复扣材料、更新订单或收取移动步数。
- **Given / When / Then**：动画过程中离开页面取消表现与回调；再次进入无旧制作事件写入新关卡。


### Story 2.4: 展示胜败和下班并支持重试

状态：可开始；依赖：2.3；覆盖：FR8。

作为玩家，我希望看懂结局并继续试玩，以便完成体验闭环。

**Acceptance Criteria**

- **Given / When / Then**：满包与步数耗尽显示不同原因；全部订单完成播放下班，不新增离场步数。
- **Given / When / Then**：可重试同关、返回首页；胜败弹窗及动画反复点击不重复结算或创建多份关卡。
- **Given / When / Then**：在Creator真实预览完整通关一次、满包失败一次、步数失败一次并成功重试，保留记录。


## Epic 3: 自己编辑关卡

### Story 3.1: 绘制与修改棋盘布局

状态：可开始；依赖：2.4；覆盖：FR1、FR9。

作为关卡作者，我希望编辑布局，以便自己制作关卡。

**Acceptance Criteria**

- **Given / When / Then**：编辑页可调整尺寸、墙、单起点、材料、设备与操作格，画笔与擦除有明确模式。
- **Given / When / Then**：非法越界与冲突显示坐标和原因，不静默截断或覆盖；本故事先用预设配方进行试玩。
- **Given / When / Then**：编辑结果可进入现有试玩，返回后布局不丢失，试玩拾取不改变编辑原稿。


### Story 3.2: 编辑配方、订单与关卡预算

状态：可开始；依赖：3.1；覆盖：FR1、FR9。

作为关卡作者，我希望调整订单与容量等参数，以便组合不同难度。

**Acceptance Criteria**

- **Given / When / Then**：设备可选择多个配方，配方可设置材料及份数，客人可配置多种食物与需求数量。
- **Given / When / Then**：可编辑全客人顺序、背包容量和步数，保存读取不丢值；7格及10步不硬编码。
- **Given / When / Then**：修改参数时显示材料需求差额，不自动破坏手工布局；试玩使用更新后的参数。


### Story 3.3: 校验关卡并安全保存草稿

状态：可开始；依赖：3.2；覆盖：FR9、FR10、NFR6。

作为关卡作者，我希望保存并定位错误，以便逐步迭代关卡。

**Acceptance Criteria**

- **Given / When / Then**：校验覆盖材料守恒、非法引用、起点数量、位置与操作格有效性；错误定位到参数或格子。
- **Given / When / Then**：允许有错误的草稿保存但不标已验证；有效性结果不等同可解性。
- **Given / When / Then**：草稿版本化保存，坏档或不兼容版本报告错误并保留原数据，不用默认值覆盖。


### Story 3.4: 导入导出并往返试玩

状态：可开始；依赖：3.3；覆盖：FR9。

作为关卡作者，我希望交换关卡配置，以便复用设计。

**Acceptance Criteria**

- **Given / When / Then**：合法JSON导出再导入后语义相同，含全部订单、队列、设备与预算。
- **Given / When / Then**：错误JSON和不支持版本不覆盖当前草稿；导入成功后可试玩再返回编辑。
- **Given / When / Then**：浏览器可下载时支持文件导出，不支持时提供文本复制与粘贴导入，不依赖Node文件系统。


## Epic 4: 验证与调整难度

### Story 4.1: 计算最少滑行解并标识结果

状态：可开始；依赖：3.4；覆盖：FR11、NFR2。

作为关卡作者，我希望知道关卡能否完成及最少步数，以便控制关卡质量。

**Acceptance Criteria**

- **Given / When / Then**：小规模已知答案关卡求出相同最短步数和可复现路径，使用游戏同一转移规则。
- **Given / When / Then**：正确包含即时满包失败、订单优先级、补位连做及停靠条件，不允许求解器自由重排订单。
- **Given / When / Then**：无解只能在完整搜索定义范围后报告；预算内无解与全局无解分开，解长度超过预算应明确提示。


### Story 4.2: 限制计算并丢弃过期结果

状态：可开始；依赖：4.1；覆盖：FR11、NFR4。

作为关卡作者，我希望在计算时继续操作，以便避免工具卡死。

**Acceptance Criteria**

- **Given / When / Then**：可配置时间和状态上限，分批让出执行；取消与超限返回未确定，不报无解。
- **Given / When / Then**：仅找到可行解未证明最短时显示仅可行；已证明最优与未确定标签不可混淆。
- **Given / When / Then**：搜索中修改配置后旧结果不应用；离开页面可取消；用基准关卡记录耗时、状态数和可支持范围。


### Story 4.3: 回放解法并管理验证状态

状态：可开始；依赖：4.2；覆盖：FR11。

作为关卡作者，我希望逐步检查最优路径，以便确认求解与游戏一致。

**Acceptance Criteria**

- **Given / When / Then**：路径能在实际规则中回放到全部订单完成，逐步展示位置、背包、订单和步数。
- **Given / When / Then**：结果绑定规则版本与关卡内容，任何影响玩法的编辑使认证失效。
- **Given / When / Then**：只有已证明最优且解不超过预算才标验证通过；超限和仅可行能存草稿但不伪称已认证。


### Story 4.4: 按最优解建议步数预算

状态：可开始；依赖：4.3；覆盖：FR12。

作为关卡作者，我希望获得可解释的预算建议，以便调整容错。

**Acceptance Criteria**

- **Given / When / Then**：已证明最短步数L时，根据作者选择的非负容错k建议L+k，不能推荐低于L的值。
- **Given / When / Then**：未证明最优时不拿可行路径长度冒充L，可明确显示当前已知解作为参考。
- **Given / When / Then**：建议先预览再应用，可撤回；应用后重新检查预算有效性及验证状态。


### Story 4.5: 生成受约束的布局调整候选
